## 2. Duplicate "pull request opened" events per thread (fix upstream)
Some PR threads carry multiple "pull request opened" events from distinct actors (apparent reopens / mis-attributed events), so member-level open counts (distinct threads per actor) sum to more than the repo's distinct-thread open count, pushing sum(prob_open) > 1 in the staged model.
Currently hotfixed downstream in `source/derived/model_prediction/build_event_time_member_panel.py` (SeparateActionTypes keeps only the earliest open per thread).
The real fix belongs upstream in `source/scrape/extract_github_data/code/transform_event_to_repo_level.py` so every consumer of the action data sees one opener per thread; once fixed there, remove the downstream hotfix. 

## 3. Duplicate "pull request merged" events per thread (fix upstream)
~0.113% of merged threads (4,746 of 4.2M) carry more than one "pull request merged" event — mostly exact-duplicate rows (same actor, same timestamp), a few genuine re-merges (reopen/reclose). They arise where `combine_action_data.py` relabels closed-PR events with a `pr_merged_by_id` as "pull request merged". Member-level merge counts (distinct threads per actor) then sum to more than the repo's distinct-thread merge count, which (with the first-reviewer fix) could push prob_review + prob_merge_direct just over 1 and crash the multinomial draw.
Currently hotfixed downstream in `source/derived/model_prediction/build_event_time_member_panel.py` (SeparateActionTypes keeps only the earliest merge per thread), mirroring the opener hotfix above. Repo-level counts already use distinct threads (`.nunique()`) so they are unaffected; `org_outcomes.py` / `investment_in_new_talent.py` count merge events per period and remain inflated by ~0.113%.
The real fix belongs upstream in `transform_event_to_repo_level.py` alongside the opener fix so every consumer sees one merger per thread; once fixed there, remove both downstream hotfixes.
