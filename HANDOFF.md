## 3. Duplicate "pull request merged" events per thread (fix upstream)
~0.113% of merged threads (4,746 of 4.2M) carry more than one "pull request merged" event — mostly exact-duplicate rows (same actor, same timestamp), a few genuine re-merges (reopen/reclose). They arise where `combine_action_data.py` relabels closed-PR events with a `pr_merged_by_id` as "pull request merged". Member-level merge counts (distinct threads per actor) then sum to more than the repo's distinct-thread merge count, which (with the first-reviewer fix) could push prob_review + prob_merge_direct just over 1 and crash the multinomial draw.
Currently hotfixed downstream in `source/derived/model_prediction/build_event_time_member_panel.py` (SeparateActionTypes keeps only the earliest merge per thread), mirroring the opener hotfix above. The real fix belongs upstream in `transform_event_to_repo_level.py` alongside the opener fix so every consumer sees one merger per thread; once fixed there, remove both downstream hotfixes.

## 9. Toggling SCons between `run` and `extended` mode (staged, not implemented)
Every SConscript currently hard-codes the `run` phase: it reads `CONFIG["<axis>"]["run"]` (Python) / `ExtractConfigValues(...)` (R), so only the `run` values of each axis (`outcome_samples`, `qualified_samples`, `importance_types`, `rolling_periods`, `control_groups`, plus the model-prediction axes) are ever built. `extended` is opt-in and disjoint from `run` (`run ∩ extended = ∅`), so "extended mode" means building the union `run ∪ extended` — e.g. adding the `same_period`/`observed` outcome samples alongside `opened_cohort`.
Proposed mechanism (mirrors how `Export('env')` already flows to SConscripts; do NOT reuse JMSLab/Template's `env.Mode`/`--mode`, which is a separate dev-only tool-isolation switch, not a spec-selection one):
1. In `SConstruct`, add `AddOption('--phase', dest='phase', type='string', default='run')` and derive `BUILD_PHASES = ("run",) if GetOption('phase') == 'run' else ("run", "extended")`, then `Export('BUILD_PHASES')`.
2. In each SConscript, `Import('BUILD_PHASES')` and replace the hard-coded `["run"]` reads with the existing `FlattenConfigValues(block, phases=BUILD_PHASES)` (Python — it already accepts a `phases` tuple) / the R equivalent in `ExtractConfigValues`. Because the blocks are disjoint, `run` mode is byte-identical to today and `extended` mode appends the extended values.
3. Invoke with `scons --phase=extended`. Targets for the extra outcome samples/samples appear automatically; `run`-mode outputs are untouched (same paths), so switching modes never rebuilds the `run` tree.
Scope note: the axes are read in ~a dozen SConscripts (event_study, event_study_forest, model_prediction, model_event_study, summ_stats, figures, analyze_forest, derived/analysis_panel, derived/model_prediction). This is a mechanical sweep once the `SConstruct` option + export exist; the paper-facing `primary_*` selectors (`paper_settings.json`) stay on `run` values regardless of phase, so `extended` mode only widens what is built on disk, never what the paper reads.
